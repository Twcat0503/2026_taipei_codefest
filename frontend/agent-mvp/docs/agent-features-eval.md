# 填表以外的功能：路由、緊急求助、附近無障礙設施

延續[填表評測](form-fill-eval.md)，把同樣的方法用在三個不是填表的功能上：

- 另請沒看過程式的代理出題。
- 規則、模型、App 實際流程分開量。
- 修改後再用新題目驗證。

- 評測：[`tests/agent-features.eval.ts`](../tests/agent-features.eval.ts)
  - `FEATURE_EVAL_SET=routing|routing2|emergency|emergency2|places|places2`
- 題目：
  - 第一批：`tests/routing-cases.ts`、`tests/emergency-cases.ts`、`tests/places-cases.ts`
  - 修改後用來驗證的新題目：`tests/routing-cases-2.ts`、`tests/emergency-cases-2.ts`、`tests/places-cases-2.ts`
- 「App 實際流程」是真的 `AgentRunner`：路由模型 → 專家模型 → 規則修正 → 工具。工具呼叫在工具層被記錄。
- 數字標「Mac」的是 Mac 上的 `qwen3:1.7b`，標「手機」的是 Pixel 10 Pro XL 上的 `lfm3-1.7b-q4_0`。

## 1. 緊急求助偵測

**原本**：`emergency.ts` 用關鍵字規則判斷，說到「昏倒、失火、家暴」這類字眼才跳出 119／110 撥號卡，不經過模型。

**第一批題目（60 題，35 題緊急、25 題不緊急但有誘導字眼）**：原本的規則只抓到 **8/35**，而且有 **8/25** 誤判。漏掉的例子：

- 「我爸剛剛跌倒叫不醒」「我透不過氣來」
- 「廚房一直冒黑煙」
- 「我老公又一直打我」
- 「有人一直跟著我到家門口」
- 「我真的撐不下去了」

**改法**：

1. **擴充規則：** 用一般急救與安全常識的說法，例如叫不醒、沒反應、嘴歪、口吐白沫、噎到、羊水破、冒黑煙、瓦斯味、被家人打、跟蹤、撬門、拿刀、不想活、割自己。
2. **排除條件：**
   - 「已經過去的事」「問資訊」「媒體」「玩笑或誇飾」不算。
   - 句子裡有「現在、剛剛、救命」時仍算數。
   - 「中風」要有「突然、剛剛」才算。
3. **路由模型兜底：**
   - 在路由原本的選項多加一個「緊急」，**不增加推論次數**。
   - 規則沒抓到、但模型判斷緊急時，顯示通用撥號卡（119／110／1925），由民眾自己按撥出。
   - 原話明確指向市府服務（路燈壞了、樹倒了、繳費），或是誇飾（熱死了），就不採用模型的緊急判斷。

**新題目（60 題，修改後才寫，用來驗證）**：

| 做法                                               |      抓到 | 誤判 |
| -------------------------------------------------- | --------: | ---: |
| 原本的規則                                         |     10/35 | 5/25 |
| 改寫後的規則                                       |     17/35 | 3/25 |
| **規則＋路由模型兜底（Mac）**                      | **32/35** | 6/25 |
| 規則＋路由模型兜底（手機，加上服務／誇飾排除之前） |     26/35 | 6/25 |

第一批題目用改寫後的規則：34/35、誤判 1/25。這批是看著寫的，數字偏樂觀。

**限制**：

- **規則有上限：** 光靠規則，新題目只抓到一半。「把藥全部吃掉」「站在河堤邊想跳」「小孩轉頭就不見了」都要靠模型。
- **模型兜底有代價：** 多出幾個誤判。誤判只會多顯示一張撥號卡，但那一題原本的需求沒被處理。
- **手機比 Mac 弱：** 手機上的模型兜底，比 Mac 的 qwen3 少抓 6 題。
- **看過結果才加的條件：** 「服務優先」「誇飾排除」「現在已經不算正在發生」是看過新題目結果才加的。

## 2. 路由：帶民眾到對的服務

**原本**：`navigation.ts` 用關鍵字規則找出 27 個目的地之一，路由模型決定領域，規則再修正。

**第一批題目（50 題）**：

| 做法                           | 正確率 |
| ------------------------------ | -----: |
| 規則                           |    54% |
| 只靠模型（從 27 個服務挑一個） |    32% |
| App 實際流程（規則＋模型）     |    68% |

**改法**：

1. **擴充各服務的說法：**
   - 看病的錢、住院費 → 醫療費；自來水 → 水費；註冊費 → 學雜費
   - 排到幾號、等多久 → 臨櫃叫號
   - 真人、客服 → 1999
   - 積水、倒樹、坍方 → 災情通報
   - 垃圾、流浪狗、人行道壞了 → 有話要說
   - 繳成功了沒 → 繳費紀錄
   - 通知我、提醒我 → 訂閱
   - 65 歲 → 長者服務
   - 網路上辦、證明 → 申辦服務
   - 我買的票 → 票券錢包
2. **找地點的判斷排除：** 報案、遺失、「怎麼註冊」「怎麼收費」這類問題，以及捷運、公車班次。

**新題目（60 題）**：

| 做法                    |    正確率 |
| ----------------------- | --------: |
| 原本的規則              |     38.3% |
| 擴充後的規則            |     48.3% |
| **App 實際流程（Mac）** | **60.0%** |

**限制**：口語換句話說還是最大的弱點，特別是繳費的細項，例如「平價住宅每個月維持大樓的錢」「在職進修班的費用」。路由模型和「只靠模型」都幫不上忙，1.7B 模型從 27 個選項裡挑一個只有三成正確。

## 3. 附近的無障礙設施（GPS）

**原本**：

- 只有原話說了「附近、最近」才會用手機位置。
- 模型會把地標填進只能放行政區的欄位，例如「台北車站」「台大醫院」。

**GPS**：

- App 端已有 `LocationMessageHandler`（geolocator），網頁經 bridge 取得位置。
- 這次在手機上實測拿到真實座標，精度約 15 公尺。
- 位置只交給工具算距離，不送進模型。

**改法**：

1. **沒提到任何地點就用 GPS：** 例如「我要找無障礙廁所」直接用目前位置。說「附近、這裡、我在的地方」也用 GPS。
2. **地標換算行政區：** 新增 [`landmarks.ts`](../src/agent/skills/landmarks.ts)，涵蓋車站、醫院、夜市、景點，例如士林夜市 → 士林區。
3. **行政區欄只收台北 12 區：** 模型填的地標名稱或猜測會被修正或丟掉。
4. **無障礙要有依據：** 原話提到（或個人設定開啟）才加，模型猜的會拿掉，例如親子廁所不算。
5. **詢問用法不算找地點：** 「怎麼註冊」「怎麼收費」、報案、交通班次都排除。

**第一批題目（45 題，修改前的程式）**：App 實際流程 68.9%（Mac）。工具選對 93%，錯誤集中在地標。

**新題目（45 題，修改後）**：

| 做法                    |    正確率 |
| ----------------------- | --------: |
| **App 實際流程（Mac）** | **93.3%** |

剩下的錯誤：「公廁壞掉了要跟哪裡反映」應該是陳情，「YouBike 騎一次多少錢」是問費用。

## 手機實測的狀況

手機連續跑推論時，有幾種情況會把模型停掉，導致後面的題目全部失敗：

- **App 退到背景：** 例如螢幕自動鎖定或切到別的 App。Android 會以背景 CPU 用量過高為由停掉模型子行程。
- **畫面轉向：** 頁面會重新載入。
- **溫度：** 手機升到約 38～39°C 時推論明顯變慢（單題 30～40 秒）。

評測時手機要保持亮螢幕、停在安心助手頁。手機腳本已改成等模型真的啟動後才開始；評測也改用與 App 相同的 90 秒推論上限。
